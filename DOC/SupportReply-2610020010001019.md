7. Why the app requires headless execution and how it is used
First, a clarification: RoxaZip is not a background app and does not run unless
the user starts an operation. The package declares three <Application> elements
because the two helper executables each need an execution alias; that alone does
not make the package a headless app. The package validator reports "headless
app" and rejects the upload only when AppListEntry="none" is added to the two
helper applications - the change this waiver request is about. The three
elements are:
- RoxaZipFM.exe: the main program, the file manager, shown as "RoxaZip" in the
  Start menu;
- RoxaZip.exe: the console program, started by the user from a command prompt or
  by scripts; it also provides the 7z.exe execution alias;
- RoxaZipG.exe: the GUI helper, which shows the archive dialogs and the progress
  window; it is started by the file manager (Add to archive, Extract, Test) and
  by the Explorer context menu (Add to archive, Extract, Test, hash), and it
  also provides the 7zG.exe execution alias.
In the published 26.3.23.0 the two helpers still appear in the Start menu as
"RoxaZip Console" and "RoxaZip GUI"; the next submission will hide them with
AppListEntry="none".
They do not run without the user: each starts only when the user initiates an
operation, runs in the user's session with the user's token, and exits when the
operation is finished.
One clarification to avoid a misunderstanding of my earlier description:
RoxaZipG.exe does show the progress window or dialog of that operation, but it
has no standalone main window; it is normally started by the file manager or the
context menu, and the 7zG.exe execution alias also allows command-line use.

8. Why this headless execution is essential, considering that it touches a
   Store control meant to empower and inform users
"Headless" here refers only to the AppListEntry setting, not to background
execution; that setting is necessary for the next update.
The published version 26.3.23.0 passed certification with one required fix,
10.1.1.11 On Device Tiles. The certification report says: "Your submission
installs multiple components to the device. Please make sure the additional
installed components that are visible in the Start Menu have a unique name that
clearly identifies which item is the main product." The fix has to be included
in the next submission, and the report shows the three entries with the same
icon.
AppListEntry="none" is the standard way to handle helper executables and is our
preferred fix for those entries. The Start menu then keeps a single, clearly
identified entry for the main product RoxaZip; the package itself remains
visible in Installed apps and can be inspected and uninstalled normally.
The waiver only affects the AppListEntry restriction; the user-facing controls
remain:
- The main application remains in the Start menu and in Installed apps; the
  user can start, inspect and uninstall it normally.
- The two helpers are installed only as part of the same Store-signed MSIX and
  remain available through the execution aliases, the Explorer context menu and
  the file manager; their command-line use is documented in the product
  documentation.
- Installation, signing, updates and uninstallation remain fully under Store
  control. The package contains no separate installer and installs nothing
  outside the MSIX.
We also cannot remove the two <Application> elements: an execution alias
(for example 7z.exe or 7zG.exe) can only be declared by the <Application>
element that declares the executable, and the file manager cannot declare
aliases for other programs. Removing them would break the 7-Zip command-line
compatibility that the product documents and supports. Renaming the entries is
the alternative, but it would keep two separate-looking Start entries; for
helper components without a standalone app experience, hiding the entries is
the clearer and less misleading fix.

9. What the background app does and how its operation is limited to protect
   user safety and privacy
There is no background app. RoxaZip installs no service, driver, scheduled task
or startup entry, and no helper process continues to run after an operation
finishes (the main program window stays open until the user closes it). The two
helpers run only when invoked, and only perform the operation the user
requested, typically creating, extracting, testing or hashing an archive (the
command-line execution aliases also expose the normal 7-Zip command set).
The limits that protect users:
- They run in the current user's session with the user's token. Normal
  archiving needs no administrator rights. The Store build performs no
  machine-wide registration; its package manifest supplies the context menu and
  the file associations.
- The operation is visible: the console version writes to its console window,
  the GUI helper shows a progress window the user can cancel, and both exit when
  the operation ends.
- They access only the files and folders passed to them by the user or the
  parent process; they do not scan disks in the background or open other
  locations on their own.
- The program contains no telemetry, analytics, advertising or network client of
  its own, and it does not collect or transmit personal data. Installation,
  updates and crash reports are handled by the Microsoft Store.
- Settings are written only to the current user's registry (a package-private
  hive in the MSIX build) and disappear with the package.
- The package contains no installer scripts, installs nothing outside the MSIX,
  and every binary comes from the Store-signed package.

Please let me know if you need any further information, for example verification

## Notes

* The Store's headless rule concerns `AppListEntry="none"` only; the three
  `<Application>` elements alone are what the published 26.3.23.0 has, and that
  package passed certification. The reply starts by separating these two ideas
  so the reviewer does not read "headless" as "background execution".
* The earlier ticket text said the two helpers have "no user interface of their
  own". The GUI helper does show the operation's progress dialog; the reply
  keeps the accurate wording so that the new answer does not contradict the
  earlier message.
* `PRIVACY.md` still contains the sentence "the program has no update checker".
  The reply therefore says that the program has no telemetry, analytics,
  advertising or network client of its own and that updates are handled by the
  Store, instead of repeating "no update checker". If a future Store package
  ships the optional Help -> Check for updates entry that master adds, the
  policy sentence should be tightened before that package is published; that is
  independent of this waiver case.
* The support case is handled in the existing thread. Do not open a second case:
  a duplicate (2610070010000866) was already closed as such on 2026-10-08.
